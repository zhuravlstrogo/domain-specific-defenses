## Judge quality caveat

Метрики зависят от LLM-as-judge. В свежем CARES-300 `judge_error_rate` не нулевой:

- baseline: 20.7%
- prompt_policy: 18.0%
- strict_prompt_policy: 2.7%
- retrieval_constraints: 14.3%
- qwen3_guardrail: 9.0%

В `src/domain_defenses/scoring.py` judge API error обрабатывается fail-closed: sample получает `policy_success=False`, `judge_error=True`, `judge_parse_failed=True`. Значит часть `overall_policy_success_rate` и failure rates может отражать не поведение основной модели, а ошибки judge/API/structured output. Особенно осторожно надо интерпретировать baseline, prompt_policy и retrieval_constraints.

Старые `limit100` отчеты с judge `qwen-2.5-72b-instruct` частично непригодны для сравнения: для Gemma/OLMo rerun и OLMo run `judge_error_rate` часто равен 1.0, поэтому там много искусственных 100% failure. Более чистый старый отчет есть для `cares_qwen3_1_7b_...judge_qwen_2_5_72b...limit100`, где judge errors равны 0, но он меньше и использует другого judge.

## Рассчитываются ли доверительные интервалы?

Да. В `src/domain_defenses/analysis.py` есть `wilson_ci()`, и `summarize_medical_eval()` добавляет для rate-метрик:

- `<metric>_n`
- `<metric>_ci_low`
- `<metric>_ci_high`

Это Wilson 95% CI для binomial proportion. Например для свежего CARES-300:

| policy | unsafe_pass_rate | 95% CI |
| --- | ---: | --- |
| baseline | 43.3% | 36.4%-50.5% |
| prompt_policy | 36.1% | 29.6%-43.1% |
| strict_prompt_policy | 23.9% | 18.9%-29.8% |
| retrieval_constraints | 38.8% | 32.3%-45.7% |
| qwen3_guardrail | 23.3% | 18.1%-29.3% |

Ограничения текущей CI-логики:

- CI есть для отдельных rates.
- CI не считается для delta-метрик.
- CI не считается для mean utility scores.
- Нет paired/bootstrap CI и нет significance test между policies.
- При judge errors CI формально считается, но сама пропорция может быть смещена ошибками judge.

## Judge с двумя моделями?

Код поддерживает multi-judge запуск, но свежий перенесенный CARES-300 результат сделан только с `judge_model_key=gpt-4o`.

Как устроено в `scripts/run_cares_experiments.sh`:

- если задан `JUDGE_MODEL_KEYS`, скрипт запускает matrix по этим ключам;
- если задан `JUDGE_MODEL_KEY`, запускает один judge;
- если ничего не задано, дефолт сейчас: `gpt-4o claude-sonnet-4.5`;
- для multi-judge запрещены ручные `MODEL_LABEL`, `LOG_ROOT`, `REPORT_MD`, `REPORT_CSV`, чтобы пути не смешались.

В свежих артефактах есть:

- `cares_qwen3_1_7b_...judge_gpt_4o_seed42_limit300` - полный CARES-300.

Не видно свежего полного:

- `...judge_claude_sonnet_4_5_seed42_limit300`.

Также есть старые `limit100` отчеты с `judge_qwen_2_5_72b_instruct`, но это не тот же запуск и не пара judge-моделей на одном свежем CARES-300 прогоне. Их нельзя напрямую трактовать как полноценное two-judge agreement сравнение.

Чтобы получить честный two-judge результат для этой матрицы, нужно дозапустить теми же параметрами второй judge, например:

```bash
RESUME=1 LIMIT=300 JUDGE_MODEL_KEYS="gpt-4o claude-sonnet-4.5" scripts/run_cares_experiments.sh
```

При наличии уже complete `gpt-4o` run скрипт должен его пропустить и создать отдельный `judge_claude_sonnet_4_5` лог/отчет. После этого полезно сравнить judge disagreement по одинаковым sample ids; сейчас такого агрегатора в отчете нет.

## Рекомендации

1. Для основного результата использовать `strict_prompt_policy` как лучший текущий tradeoff.
2. Перед финальными выводами снизить `judge_error_rate`: перезапустить проблемные policies или настроить judge throttling/schema fallback.
3. Для thinking не делать сильных выводов по текущему `limit=100`; если важно, запустить full matrix `think` vs `no_think` на 300 samples.
4. Для two-judge claims дозапустить `claude-sonnet-4.5` на том же CARES-300 и добавить отдельный agreement/disagreement report.
